- M2-05: HTTP client pool. `internal/monitor/httpcheck/pool.go`: `Pool` keeps one `http.Transport` per connection-relevant key (insecure TLS, proxy URL, IP family) and hands out a cheap per-check `http.Client` carrying the redirect policy (off → the 3xx is the result; on → at most 10 redirects, then `ErrTooManyRedirects`). Unused transports are evicted after 10 min by a lazy sweep (at most once a minute, on the next request; no goroutine); `Close` empties the pool. Tests: key sharing and separation, 5 checks on one connection, eviction and sweep throttle on a fake clock, exactly 10 redirects followed and 11 refused (mutation-checked: `>=` turns it red), ipv6 cannot reach 127.0.0.1, 32 goroutines under `-race`.
- M2-06: HTTP check executor. `(*httpcheck.Pool).Check(ctx, Config) Result` never returns an error: every failure is a kind + message (+ snippet for HTTP failures). Request: GET/HEAD/POST (body only for POST), within `context.WithTimeout(Timeout)`, headers applied in the order User-Agent (custom, else `Sinjal/<ver>` given to `NewPool`), plain headers, secret headers (`header.<Name>`), auth (`auth.basic` → Basic, `auth.bearer` → Bearer); later wins. Kinds: `timeout dns connect tls http_status body_assertion json_assertion json_parse protocol unknown`; `classify` maps deadline/net timeouts, `*net.DNSError`, TLS verification/x509/record/alert errors, `*net.OpError`, and falls back to `protocol` (malformed response, early close, > 10 redirects); caller cancellation is `unknown`. Status mismatch → `http_status` with a ≤ 4 KiB snippet; success keeps no body data (early stop: at most 4 KiB drained for connection reuse). Snippets and messages are scrubbed of every secret value, the basic password and its base64 form; the snippet reads the longest secret's length past the cap and scrubs before cutting, so a secret straddling the cut leaves no prefix (mutation-checked), then is made valid UTF-8 and kept ≤ 4096 bytes. `readCapped` (LimitReader cap+1, truncation flag) is ready for M2-07's 1 MiB body cap. `store.Secrets` decrypts a monitor's secrets as `secret.String` for the executor. Tests on httptest servers: methods and POST body, header/auth/UA precedence, 503 snippet, expected 503 succeeds, secret echo scrubbed at the boundary, invalid UTF-8 and mid-rune cut, 2 MiB read capped, 100 ms timeout cancels, cancelled parent → unknown, dns (.invalid), connect (closed port), tls (self-signed; passes with insecure), protocol (garbage reply, redirect loop). `BenchmarkCheck` (local, reused connection): ~75 µs, 88 allocs per check. Not wired into a scheduler yet (M2-10..12).
- M2-07: Assertions. `monitor.JSONPath.Resolve`, `DecodeJSON` (`UseNumber`, last duplicate key wins, trailing data is an error) and `EvalJSONAssertion` implement P0-07: numbers compare exactly via `big.Rat` (`1` equals `1.0`, no float loss), strings bytewise, bool/null by value, `42` never equals `"42"`, containers never equal scalars, `not_equals` fails on a missing path, `null` exists. `httpcheck.Config` gains `BodyContains`, `BodyNotContains`, `JSONAssertions`; `Check` reads the body (`readCapped`, `MaxBodyBytes`) only when one is set, else keeps the short drain. Text mismatch → `body_assertion`; truncated or invalid JSON → `json_parse`; failed assertion → `json_assertion` with a snippet of path, operator, expected and actual (actual cut to 200 bytes). Snippets go through the shared `scrubber.clip` (scrub, cut, valid UTF-8). Status failures still come first; success keeps no body. Tests: evaluator type matrix, text case-sensitivity, parse failures incl. a valid prefix cut at the cap, scrubbing, read cap. Mutation-checked: number comparison, `not_equals` negation, contains polarity, truncation guard.
- M2-08: TLS metadata. `httpcheck.Result.TLS` (`*TLSInfo`: `NotAfter` UTC, `Issuer`, `DaysRemaining`) is read from `resp.TLS.PeerCertificates[0]` (the leaf) for every HTTPS response, before the status and body checks, so it is kept on failed checks too; days are `floor((NotAfter - Pool.now)/24h)` and go negative once expired. `Result.MetadataJSON()` renders the `metadata_json` value `{"tls":{"not_after","issuer","days_remaining"}}` ("" for plain HTTP or when no handshake completed, so callers store NULL); the issuer is scrubbed like the message. Invalid or expired TLS still fails as `tls` via `classify` and carries no metadata (no response); `Config.Insecure` lets it pass and the expiry is still reported. Warning thresholds and `monitors.tls_not_after` persistence stay with the scheduler/result processor milestones, and the Advanced-only warning for insecure TLS belongs to the UI. Tests use generated self-signed certificates (`certServer`) with a fixed `Pool.now`. Mutation-checked: floor, TLS capture. Not covered: leaf-vs-chain order (test servers send one certificate).
- M2-09: state machine. `internal/incident`: `Transition(state, counters, success, thresholds) → Outcome{State, Counters, Retry}`, pure (no clock, no DB). UP and PENDING share one branch: success → UP, failure → PENDING + `Retry` until the failure threshold → DOWN (threshold 1: straight to DOWN, no retry); DOWN leaves only after the success threshold, a failure in between resets the count, and DOWN never asks for a retry; PAUSED and unknown states are returned unchanged. At most F − 1 retries in a row. No DEGRADED, no incident rows, no flapping (M3). Tests: exhaustive table (5 states × 2 results × 9 threshold pairs × 16 counter values), named flows for AGENTS §6 (failure → retry → down, retry success, recovery, full cycle), retry bound for F = 1..100. Mutation-checked: `>` instead of `>=` at the failure threshold turns 9 tests red. Threshold rules written into `10_INCIDENTS.md`. Not wired yet: the result processor (M2-12) calls it.
- M2-10: scheduler. `internal/scheduler`: `queue` (min-heap via `container/heap` plus an index by id; pure, every method takes `now`) and `Scheduler` (one goroutine, one command channel, one `time.Timer`). Commands: `Set(id, interval, delay)` covers add and update (an edit replaces the schedule and checks at once), `Remove` covers delete, pause and disable, `RunNow`, `Retry(id, delay)`. Each entry has a fixed cadence (`regular`) and a heap key (`at`); a retry or run-now only pulls `at` earlier and is flagged `Job.Retry`, so the cadence never moves, and a retry that would land at or after the next regular run is not added. Ties go to the retry. More than an interval behind → missed runs skipped. Jitter: fixed per-monitor offset `FNV-1a(id) mod min(interval/10, 30 s)`, applied once after the first check, so the first check is prompt and later gaps are exactly the interval. Times keep the monotonic reading (`time.Now()` values, never re-parsed). `dispatch func(Job)` must not block (the pool's `Submit`, M2-11). Tests: heap rules with fixed times, 20,000 random operations checking the heap/index invariants, jitter bounds for 10 s..24 h, and the loop under `testing/synctest` (virtual clock, exact fire times, 1,000 monitors added in one instant spread over the window, stop leaves no goroutine and no blocked caller), plus concurrent commands under `-race`. Mutation-checked: tie-break, fall-behind skip, retry moving the cadence. `07_SCHEDULER.md` documents commands, jitter and the retry rule. No clock interface in production code. Not wired into `serve` (M2-13); benchmarks are M2-20.
- M2-11: worker pool. `scheduler.Pool` (`internal/scheduler/pool.go`): `NewPool(workers, queue, run, log)`, `Run(ctx)`, `Submit(Job)`, `Stats()`. Worker count is the existing `config.Workers` (`SINJAL_WORKERS`, default `min(32, max(8, NumCPU*4))`, M0-04), so nothing changed in `internal/config`. Two bounded channels of `DefaultQueue` = 1024 (retries/run-now and regular); workers take retries first through a nested `select`. `Submit` never blocks: a full queue drops the job and counts it (`Rejected`), which is the defined overload behaviour (the monitor runs again at its next interval, memory stays bounded). A start more than 1 s after `Job.Due` counts in `LateStarts` / `MaxLate`. One WARN per minute at most. Cancel: the context reaches `run`, waiting jobs are abandoned, no job starts after cancel, `Run` returns when the workers are out. A panicking check is logged with its monitor id and the worker survives. Tests under `testing/synctest`: concurrency limit, retry order, queue bound and rate-limited warning, late-start accounting, cancel, panic, 1,000 monitors due at once through 8 workers with nothing dropped, and stuck workers not stopping the scheduler (it keeps dispatching and applying commands); a real-goroutine test under `-race` checks no job is lost uncounted. Mutation-checked: retry priority, start-after-cancel guard, blocking submit. Two test-only lessons: a blocked `select` is resolved by the event that wakes it (so the cancel guard only matters for a worker returning from a check), and "queue empty and nothing active" is not a safe idle test. `07_SCHEDULER.md` documents queue size and overload behaviour. Not wired into `serve` (M2-13).
- M2-12: result processor. New `internal/results`: `Processor` with `Add(ctx, Result) bool` (blocks while the 256-result channel is full), `Run(ctx)` (one goroutine; on cancel it drains the channel and writes once more within 5 s) and `Stats()`. A batch is flushed at 128 results or 200 ms after its first result; the timer is armed only while something is buffered. One transaction per batch inside `db.Retry`; per result `store.GetCheckState` → `store.InsertCheckResult` → `incident.Transition` → `store.ApplyCheck` (new `internal/store/results.go`; state, state-since on change, last check / success / failure, `tls_not_after` set / cleared on a success without a certificate / kept on a failure without one). Results of one monitor in the same batch are applied in order. Counters (consecutive failures, or successes while down) are kept in memory only for monitors part-way to a change, tagged with the state and state-since they were counted in, so a pause and resume or any outside change resets them; they are lost on restart (documented in `07_SCHEDULER.md`). Effects are applied after the commit only: counters, `retry(id, retryDelay)` for the last outcome of each monitor (the scheduler's `Retry`), `notify(id)` once per monitor (hook for the M2-14 SSE hub), then the stats. Late results for paused or deleted monitors are discarded and counted. A batch that cannot be written (busy exhausted or any other error) is held and retried after 1 s, with an ERROR log (once a minute) and `Stats().Warning`; when the held batch is full the processor stops receiving, so the back-pressure reaches workers, pool queue and scheduler instead of memory. Tests on a real SQLite file: row contents and NULLs, scenarios 1–3, thresholds 3/3 and an edited threshold, several results per batch, flush by size and by time, paused/deleted, counter reset and cleanup, TLS expiry, busy exhaustion against a second connection holding `BEGIN IMMEDIATE`, a generic write error with `Add` blocking at exactly batch + queue, shutdown flush, concurrent `Add` under `-race`, and `TestPipelineScenarios` running the real `Scheduler`, `Pool` and `Processor` together with a scripted check (pending → down → up, pending → up, up). Seven mutations checked. Found by the tests: stats were published before the callbacks, and the failure counter before the warning; both are now published last. Not here: wiring into `serve` and building `httpcheck.Config` from a monitor (M2-13), the SSE hub (M2-14), a UI surface for the warning (M2-14 `system.warning` / M9), incidents (M3), benchmarks (M2-20).
- M2-13: startup restore and pause/resume. New `internal/engine`: `Engine` owns the `Scheduler`, the `Pool`, the `Processor` and the `httpcheck.Pool`; `Start(ctx)` reads the enabled monitors (`store.ListSchedules`: id and interval) and schedules them with first checks 20 ms apart (all within 10 s however many there are), `Wait()` returns after the shutdown order scheduler + workers, then processor (final flush), then idle connections. Restoring state needs no code of its own: it is in the monitor row and the processor reads the row per batch. The check function reads monitor, HTTP config and secrets per check (three indexed reads, nothing cached, edits apply to the next check), maps them with `buildHTTPConfig`, runs `httpcheck.Pool.Check` and maps the result with `toResult` (`tls_not_after` only while expiry checks are on). Deleted or paused: skipped; database unreadable: ERROR log and skipped; configuration or secret unusable: stored as a failed check, kind `unknown`. A check cut off by shutdown is dropped, not stored as a failure. `Pause` / `Resume` change the row (`store.PauseMonitor` / `ResumeMonitor`, new `internal/store/pause.go`: state, state-since, `enabled`, `flapping_since` cleared, `monitor_pauses` opened / closed, idempotent) and then the schedule, under one mutex. `serve` starts the engine after the listener is open and waits for it before the database closes. Tests: store (pause, resume, created-disabled, unknown id, schedule list); engine on a real SQLite file against `httptest` targets (startup, restart during an outage, pause stops checks and resume checks at once, idempotence, a waiting job of a paused monitor, a running check of a paused monitor, shutdown with a running check, shutdown with a finished one, unusable config, unreadable secret, secrets reach the request, concurrent pause/resume under `-race`); `tests/integration/m2_test.go` with the real binary over three restarts. Mutation-checked: shutdown drop guard, scheduler removal on pause, the no-op resume, the paused skip, the start spread, the immediate check on resume, the failed check for unusable config, `flapping_since`, the resume guard. Not mutation-checked: the pause/resume mutex (its window is the few nanoseconds between commit and scheduler command; no test hits it). Without the drop guard the shutdown test fails in some runs only: `Processor.Add` picks at random between its queue and the cancelled context, so the guard cannot be left to `Add`. Docs: `07_SCHEDULER.md` (start, running a check, pause and resume, shutdown), `10_INCIDENTS.md`, `20_TESTING.md`, `28_FILE_LAYOUT.md`. Not here: routes and audit events for pause/resume (M2-18), scheduling on create/edit/delete (M2-17, M2-18), closing the incident on pause (M3), other monitor types (M4).
- M2-14: SSE hub. New `internal/web/sse`: `Hub` with `Publish(event, monitorID)`, `Serve(w, r, alive)`, `Close()`, `Stats()`; event names `monitor.created|updated|deleted`. `Publish` serialises a frame once (`id` = counter of all events, `event`, one-line JSON `{"monitor_id": …}`) and offers it to every client's 256-frame channel without blocking; a full channel means the client is removed and its stream closed (WARN, `Dropped`). `Serve` sends an opening comment with `retry: 3000`, then frames (everything waiting in one write), a `: keepalive` comment every 20 s, and ends on client disconnect, failed write, hub close or a vanished session. Each write gets a 10 s deadline through `http.ResponseController`, because `WriteTimeout` would otherwise end every stream after 30 s. No replay on `Last-Event-ID`: a browser refreshes when its stream opens (M2-15). `web.RegisterEvents` mounts `GET /events` behind `RequireAuth` (admin and viewer) and re-checks the session at every keepalive (`sessionAlive`: only `ErrNoSession` ends the stream, a database error is logged). `serve` creates the hub, passes `Publish(monitor.updated)` to the engine (`engine.New` gained `updated`; the processor calls it per monitor per stored batch, `Pause` / `Resume` when they changed something) and registers `Hub.Close` with `RegisterOnShutdown`. Tests: hub over a real server (order, ids, headers, slow client dropped while a healthy one gets everything, 10,000 publishes against a client that never reads, close ends streams cleanly and refuses new ones, disconnect), under `testing/synctest` with a fake writer (keepalive timing, per-write deadline, session check ending the stream, burst written in one write, failed write), concurrent subscribe / leave / publish / close under `-race`; route table (signed out and bad cookie redirected, admin and viewer streams with security headers, stream alive after four times the server's read and write timeouts, session check for logout, disabled viewer and database error); engine announcements; `tests/integration/m2_test.go` with the real binary (event delivered for a stored check, SIGTERM with an open stream exits cleanly at once). Mutation-checked: per-write deadline (route test and synctest), slow-client drop, session check, closed-hub refusal, unsubscribe on return, burst drain, flush, route mounting, both branches of `sessionAlive`, the shutdown hook (without it the binary waits out the 10 s grace). A mutation check also removed code: the handler cleared the read deadline on the assumption that `ReadTimeout` cancels a streaming request; removing the call broke nothing, and `net/http` (`startBackgroundRead`) clears that deadline itself once a bodiless request is read. `BenchmarkPublish` (one event to 8 clients, each taking it): ~0.9 µs, 192 B, 4 allocations per event on the development machine. Docs: `32_SSE_EVENTS.md` (implementation), `13_AUTH_SECURITY.md`, `16_DEPLOYMENT.md` (proxy buffering, HTTP/2), `07`, `09`, `20`. Not here: senders of `monitor.created` / `monitor.deleted` (M2-17, M2-18), the browser side and fragments (M2-15), `system.warning` and the other event names (with their features).
